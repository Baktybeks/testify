# Exam platform

Платформа экзаменов: React 19, TypeScript 5.9, Vite 7, TanStack Query 5 и Supabase. Фронтенд размещается на GitHub Pages, бизнес-правила выполняются транзакционно в PostgreSQL. Google Sheets и Apps Script для работы не нужны.

Подключён проект Supabase `testify` (`frnpbbpmxpmlpkhunzxd`, Singapore). Миграции применены, функция manage-account опубликована. 60 исходных вопросов и 6 групп перенесены в черновик первого модуля, доступ групп закрыт. Публичная конфигурация проекта находится в `src/shared/public-config.json`; это publishable key, серверных ключей в файле нет. VITE-переменные при необходимости переопределяют эту конфигурацию.

## Локальный запуск

Нужен Node.js 24.

```sh
npm ci
cp .env.example .env
npm run dev
```

Для подключённого проекта копировать .env не обязательно. Для другого проекта в Windows используйте `Copy-Item .env.example .env` и заполните публичные параметры Supabase.

```sh
npm test
npm run build
```

## Supabase

1. Создайте отдельный Supabase-проект, выберите подходящий регион. Не используйте рабочий экзамен для нагрузочных тестов.
2. Установите Supabase CLI. Выполните `supabase login`, `supabase link --project-ref YOUR_REF`, `supabase db push`. Альтернатива: примените файлы из `supabase/migrations/` в SQL Editor по порядку; каждый целиком в транзакции.
3. В Auth отключите публичную регистрацию и анонимные входы. Включите ограничения частоты входа; перед массовым экзаменом проверьте их на стенде. Локальные настройки находятся в `supabase/config.toml`; удалённые Auth settings проверяются отдельно.
4. Создайте преподавателя: задайте в окружении `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `TEACHER_EMAIL`, `TEACHER_PASSWORD` (12+ символов), `TEACHER_NAME`; выполните `node scripts/create-teacher.mjs`. Секреты не указывайте в аргументах команд и не сохраняйте в Git. Скрипт также подходит для создания второго преподавателя.
5. Edge Function по умолчанию разрешает origin `https://baktybeks.github.io`. Для другого хоста задайте `supabase secrets set ALLOWED_ORIGIN=https://YOUR_HOST`; затем `supabase functions deploy manage-account`. Для локального создания аккаунтов используйте origin вашего Vite-сервера. Функция сама проверяет JWT через Auth и роль в базе; `verify_jwt=false` отключает только проверку шлюза.
6. Во фронтенде укажите `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` (publishable/anon key). `service_role` запрещено помещать в VITE-переменные.

Студент входит логином и индивидуальным кодом. Auth использует технический адрес `<login>@students.testify.invalid`; почта студенту не нужна. Новые коды показываются при создании/сбросе, в таблицах приложения они не хранятся. Сброс пароля не является отзывом уже выданного access token; для немедленного запрета используйте блокировку студента, проверяемую на каждом RPC.

## Первый экзамен и перенос Excel

### Импорт JSON с общим паролем

При ручном добавлении студента заполняются только ФИО, логин и группа. Внутренний StudentID сервер создаёт автоматически; он не нужен для входа. Для совместимости импорт может передавать собственный ID, а JSON без id использует логин как ID.

Во вкладке «Студенты» откройте «Добавить студентов через JSON», выберите группу и вставьте массив:

```json
[
  {"name":"Иванов Иван Иванович","login":"ivanov_i_i"},
  {"name":"Петров Пётр Петрович","login":"petrov_p_p"}
]
```

Задайте общий пароль (8–128 символов), нажмите «Проверить JSON», затем «Создать студентов из JSON». Он применяется к новым записям без собственного password. Группу можно переопределить полем group, ID — полем id (по умолчанию login), индивидуальный пароль — password. Поддерживаются также FullName/Login/GroupID/StudentID/Status из таблицы. status: blocked сохраняет блокировку при создании. Уже существующие логины пропускаются; пароли существующих студентов не меняются. Общий пароль позволяет входить в любой аккаунт с известным логином — выбирайте этот режим осознанно.

Без пароля создаются индивидуальные коды. После импорта скачивается приватный CSV с выданными паролями/кодами. Пароли очищаются из полей и отчёта интерфейса; Supabase Auth хранит хеши. До 500 записей, файл до 1 МБ. Импорт идёт последовательно с паузой для серверного лимита; можно остановить. При частичном сбое список оставшихся записей возвращается в поле JSON без паролей: задайте пароль заново перед повтором. Успешно созданные аккаунты сохраняются. Перезагрузка во время импорта может прервать отчёт; перед повтором сверяйте список студентов.

Каталог: **Дисциплина → Учебный модуль → Экзамен / партия → Группы**. Во вкладке «Дисциплины» можно добавлять дисциплины и их учебные модули. Подготовлены Web-разработка (Модуль 1, Модуль 2) и UX/UI (Модуль 1, Модуль 2). Существующий экзамен с 60 вопросами относится к Web-разработка → Модуль 1. Банки: Web-разработка → Модуль 1 — 60 вопросов; UX/UI → Модуль 1 — 90 вопросов.

Во вкладке «Экзамены» выберите дисциплину и учебный модуль для новой партии. Банк вопросов принадлежит учебному модулю. У каждого экзамена свои настройки, доступ групп и результаты; все экзамены одного учебного модуля используют общий банк. Копия сохраняет связь с учебным модулем; в черновике её можно изменить. Фильтры преподавателя и экспорт результатов учитывают дисциплину, учебный модуль и экзамен. Студент видит этот путь на карточке. В API имя `module_id` сохранено для совместимости: оно обозначает экзамен; `course_module_id` — учебный модуль.

1. Войдите преподавателем и создайте группы вручную либо импортом листа `Groups`.
2. Создайте экзамен для выбранной дисциплины и учебного модуля: по умолчанию 20 вопросов, 30 секунд, 600 секунд всего, максимум 10 баллов.
3. В разделе «Вопросы» выберите дисциплину и учебный модуль (экзамен создавать заранее не нужно), загрузите XLSX (лист `Questions`) либо CSV. Проверьте предварительный отчёт, затем подтвердите импорт. Совпадающие QuestionID внутри учебного модуля обновляются с увеличением версии. Начатые попытки сохраняют прежние снимки вопросов.
4. Столбцы вопросов: `QuestionID,Lecture,Difficulty,Question,OptionA,OptionB,OptionC,OptionD,CorrectOption,TimeSeconds,Active`. CorrectOption — A–D. Время задаётся на уровне модуля; TimeSeconds из старого файла не применяется.
5. Банк может содержать 60, 90 и любое достаточное число вопросов. Режим random выбирает N разных вопросов из всего активного банка. Режим quotas выбирает заданное число по каждой теме, затем смешивает общий порядок. Например: `{"1":3,"2":3,"3":3,"4":3,"5":2,"6":3,"7":3}`. Нехватка темы блокирует открытие; автоматического перераспределения нет.
6. Импорт студентов: `StudentID,FullName,GroupID,Login,Status`. Группы должны существовать; логины — строчные латинские символы, цифры, `_`, `-`, `.`. AccessCode из исходника игнорируется. Для новых аккаунтов генерируются новые коды. CSV с кодами скачивается после импорта (в том числе частичного); храните его приватно. Импорт выполняется последовательно, не является одной транзакцией; после сбоя остаются только необработанные строки. При закрытии страницы сверяйте список созданных студентов и сбрасывайте потерянные коды.
7. В карточке экзамена отметьте группы под заголовком «Кому открыть экзамен?», нажмите «Открыть экзамен для выбранных групп» и подтвердите название, группы и сохранённые правила. Выбор групп и открытие выполняются одной транзакцией; при неготовом банке доступ не изменится. Неотмеченные группы не получат доступ. Фильтр «Группа» сверху влияет только на отображение. При необходимости задайте окна сдачи в разделе «Группы»: ввод в UTC, рядом время Asia/Bishkek. Истёкшее окно выбранной группы нужно исправить перед открытием.

Рабочие XLSX, персональные данные и ключи ответов не входят в репозиторий. Исходные Attempts/Results автоматически не импортируются: исторический перенос требует отдельного сопоставления модулей и идентификаторов. В исходной копии было только две записи Students; полный список нужно импортировать отдельно.

Новая партия: скопируйте настройки экзамена, назначьте группы и откройте новый экзамен. Копия использует банк выбранного учебного модуля без дублирования вопросов. Настройки экзамена редактируются в черновике; банк — независимо от экзаменов, изменения влияют на новые попытки. Старые снимки вопросов и оценки сохраняются. Архивные экзамены скрыты из списка доступных студенту; результаты завершённых попыток доступны в «Истории экзаменов».

## Правила времени и восстановления

Серверные часы определяют дедлайны. Ранний ответ запускает следующие 30 секунд, но не продлевает общий лимит. После отсутствия сервер догоняет пропущенные интервалы. Закрытие приёма не прерывает начатые попытки. Ответ, обрабатываемый после дедлайна, не принимается: льготного сетевого интервала нет. Клиент показывает подтверждение только после успешного RPC. Повтор использует тот же UUID команды; ответ и продвижение атомарны. После перезагрузки войдите и нажмите «Продолжить».

Публикация: только CLOSED → PUBLISHED, когда действующие попытки завершились и не осталось неиспользованных разрешений на пересдачу. Просроченные попытки сверяются при открытии панели. После публикации повторное открытие всего экзамена запрещено. При архивировании опубликованные результаты остаются доступны.

## Суперадмин, пересдачи и удаление

Роли: student, teacher, superadmin. Суперадмин обладает правами преподавателя и дополнительными правами на удаление и изменения после публикации. Роль хранится в приватном профиле и проверяется сервером на каждом вызове, не берётся из пользовательских JWT metadata.

В шапке отдельно показана роль аккаунта. Вкладка «Преподаватели» доступна только суперадмину: ФИО, email и пароль 8–128 символов создают подтверждённый аккаунт с обычной ролью teacher. Список показывает преподавателей и суперадминов без паролей. Edge Function проверяет пользователя и роль; служебная SQL-функция повторно проверяет права автора и записывает создание в аудит. Браузеру эта служебная функция недоступна.

Во вкладке «Студенты» формы JSON-импорта, ручного создания, файлового импорта и список сворачиваются в аккордеоны. Новый пароль после создания или сброса показывается в отдельном окне с логином; по почте он не отправляется.

В карточке черновика экзамена есть «Удалить экзамен»: требуется точное название. Удаляются черновик и настройки доступа групп; банк вопросов учебного модуля, сам учебный модуль и студенты сохраняются. Сервер блокирует удаление при наличии попыток, счётчиков запусков или разрешений пересдачи. Действие фиксируется в аудите.

В «Попытки и результаты» преподаватель выбирает «Разрешить пересдачу», вводит причину и срок начала (по умолчанию 24 часа, ввод UTC). Прежняя попытка аннулируется с сохранением ответов, прогресса, причины и автора; её оценка исключается из итогов. Разрешение выдаёт ровно один новый запуск, таймер начинается при нажатии студентом «Начать пересдачу». Повторных разрешений может быть сколько нужно, каждое имеет отдельную причину. Неиспользованное разрешение можно отозвать. Новое разрешение заменяет прежнее неиспользованное, а не складывается с ним. Пересдача может начинаться при закрытом приёме для всей группы до указанного срока.

После публикации пересдачу разрешает только суперадмин. Прежний результат теряет статус действующего; новая оценка остаётся скрытой до отдельного действия «Опубликовать результат». Оценивание и ответы старой попытки не переписываются.

Суперадмин может выбрать «Удалить навсегда», указать причину и вручную ввести логин студента. Удаляются выбранная попытка, ответы, снимки вопросов, команды и результат; в аудите остаются действие и причина без удалённых ответов/оценки. Удаление не выдаёт разрешение на новый запуск. Служебный счётчик сохраняется, чтобы удаление не обходило правила попыток. Для новой пересдачи после удаления выберите экзамен в фильтре и студента в блоке «Разрешить ещё одну попытку».

Журнал — `exam_private.audit_logs`, история разрешений — `exam_private.retake_grants`. Операции идемпотентны по UUID запроса. Старые вкладки не принимают ответы после аннулирования; одновременные старты расходуют одно разрешение и создают одну действующую попытку.

## GitHub / GitHub Pages

SSH remote: `git@github.com:Baktybeks/testify.git`.

1. В Settings → Pages установите Source: **GitHub Actions**.
2. При необходимости переопределите `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` в Settings → Secrets and variables → Actions → Variables. Без них используется публичная конфигурация текущего проекта из исходников.
3. Push в `main` запускает установку, SQL-тесты, многосессионный тест PostgreSQL, браузерные проверки, сборку и публикацию `dist`.
4. Ожидаемый адрес: `https://baktybeks.github.io/testify/`. Это адрес конфигурации, а не подтверждение состоявшегося деплоя.

Используется один SPA entrypoint: внутренних pathname-маршрутов нет, поэтому обновление страницы не требует обхода 404 GitHub Pages. BASE_PATH в CI выводится из имени репозитория. Миграции Supabase намеренно не запускаются автоматически при каждом frontend push: перед ними нужен backup и отдельный `supabase db push`.

## Проверки и эксплуатация

`npm test` исполняет настоящие миграции и PL/pgSQL через PGlite: дедлайны, уникальность, оценки, квоты, идемпотентность, скрытые результаты, права и переходы. PGlite использует один embedded connection: этот прогон **не доказывает конкурентность независимых PostgreSQL-сессий или производительность Supabase**.

`npm run test:postgres` дополнительно проверяет конкурентный старт и отправку разных ответов из 8 независимых PostgreSQL-сессий. Нужен `TEST_DATABASE_URL` на пустую одноразовую базу с именем `testify_test`; скрипт не удаляет существующие схемы и отказывается работать с другой базой. Без URL тест пропускается. В GitHub Actions PostgreSQL 17 запускается отдельным service container.

`npx playwright install chromium`, затем `npm run test:e2e` проверяет мобильный поток с подменённым API (login, отправка, reload/resume, скрытый/опубликованный результат). Для него задайте `VITE_SUPABASE_URL=https://exam-test.supabase.co` и `VITE_SUPABASE_ANON_KEY=test-key`. В CI это настроено автоматически. Подмена API не является интеграционным испытанием облака.

Нагрузочный сценарий: `k6 run scripts/load-test.js`. Передайте окружением SUPABASE_URL, SUPABASE_ANON_KEY, MODULE_ID, ACCOUNTS (путь к приватному JSON `[{"login":"load_1","code":"..."}]`), VUS=150, затем 300 на новом модуле. Один отдельный студент на VU. Сценарий выполняет вход, повторный старт, ответы примерно каждые 25 сек., повторы команд и чтение текущей попытки. Цель: p95 RPC <500 мс, ошибки <1%, отсутствие потерь/дублей после проверки БД. Реальные измерения пока не выполнены; показатели не гарантируются.

Перед реальным экзаменом: полный прогон на мобильных устройствах и реальном Supabase, параллельные запросы из независимых сессий, проверка лимитов Auth, мониторинг latency/errors/DB locks в Supabase, план резервного копирования и пробное восстановление. Доступность backups/PITR и ресурсов зависит от выбранного тарифа. Отдельные JVM Actuator/HikariCP не нужны в этом стеке. Аудит административных действий находится в `exam_private.audit_logs`, секреты в него не записываются.

Подробности: [архитектура](ARCHITECTURE.md), [API](docs/API.md), [OpenAPI](docs/openapi.yaml), [приёмка](docs/ACCEPTANCE.md), [результаты проверок](docs/VALIDATION.md).
